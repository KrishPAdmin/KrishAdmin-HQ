# Pi cluster and Uptime Kuma

The Discord owner can use `hq_homelab` for live status at 192.0.2.90 (Pi-Cluster-01), .91 (Pi-Cluster-02), and .92 (Pi-Cluster-03), including host load/memory/disk/temperature, Swarm nodes/services, and authenticated Uptime Kuma monitor states from https://status.example.invalid/dashboard. Collection runs on HQ over verified SSH and verified HTTPS, with no model inference needed for the measurements.

Examples: “Show my Pi cluster and dashboard status”; “Show Swarm services”; “Restart kuma_kuma”; “Install nginx on Pi-Cluster-03 on port 8080”; “Turn off homelab DM updates”. The tool always checks the actual Discord owner and message at the host service, using signed, expiring, non-replayable origin requests. Other channel users cannot perform these operations.

Changes use a concrete persisted proposal before dispatch. An explicit owner message naming the exact restart service, or the app, target and published port, authorizes that action directly. Otherwise the proposal shows a specific apply instruction. Ambiguous command outcomes are never automatically repeated. Restart means a Swarm rolling replacement of service tasks. The tool reports command acceptance separately from readiness and never claims successful application health solely from a zero exit code.

Initial deployment catalog: nginx, httpd and Redis. Image manifests are resolved to Linux ARM64 digests before execution. New services have unique hqbot names, one replica constrained to the selected Pi, 0.5 CPU/256 MiB limits, no privileged mode, host networking or host mounts. Redis has no published host port and is explicitly ephemeral. Other apps can publish an explicitly requested port >=1024 on the target host. These are bounded app setups; arbitrary shell commands, package installation, persistent storage, custom Compose files and changing existing service configuration are not exposed. Additional recipes can be added for specific applications.

`hq-hermes-homelab-monitor.timer` checks once per minute while enabled. It compares host availability, Swarm node state, service replicas and active Kuma monitor status. The initial snapshot establishes a baseline. Subsequent changes are sent only to the verified owner DM, with allowed mentions disabled, and lost responses are reconciled before retry. This is periodic monitoring, not an instantaneous stream; timestamps and unknown/unavailable results must remain visible. Current snapshot: `state/homelab/snapshot.json`. Delivery errors: `state/homelab/monitor-error.json`. Ask the bot to disable or enable updates with `watch`.

Credential source: encrypted OpenBao entry `pi-cluster`, retrieved through the host-only `/run/hq-vault/connector.sock`. The former Codex password file has been removed. The host connector retrieves this entry and never places it in model prompts, container environments, arguments, reports or the tool schema. This protects against other ordinary local users, not root or programs already running as krishadmin. Initial enrolled SSH host keys are retained in `state/homelab/known_hosts`; changed keys fail closed.

Runtime dependencies live in `.venv-management`; recreate with the pinned `management-requirements.txt`. The existing private Unix socket owner service hosts GitHub, Workspace and homelab routes. Only the concierge holds the HMAC origin key; the language model cannot choose the caller identity or invoke a raw SSH command.
